## 数据口径

`meta.json` 中的「热门」全部是**社区推荐**：统计的是「有多少位不同作者的 BWIKI 投稿里出现了它」，**不是使用率、胜率或对局占比**。

- 同一作者反复保存的同一套阵容只算一次。
- 热门精灵/技能：按收录它的不同作者数排序。
- 热门配队：一份阵容有多少位**其他**作者投稿了至少 4 只相同精灵的阵容；与已入选阵容有 5 只以上相同的近似克隆只保留一份。逐对比较，不做传递合并（试过合并聚类，会把不同打法链在一起）。
- 每个面板都标注来源与投稿日期范围，技能数据标注模块修订日期。

## 当前赛季动向（`season.json`）

社区推荐页顶部的「S4 动向」来自 `season.json`：**人工整理**，不由定时任务生成，所以刷新不会覆盖它。只写当前赛季（S4，2026-09-10 开赛），更早赛季的阵容暂不考虑。

- 每一条都是我读到原文、能确认发布日期与出处的信息（官方公告、官方宣传、工具站更新日志）。测试会检查：日期不晚于整理日期、不早于开赛前两周、来源是 https 链接、不含使用率/胜率类字样、按时间倒序。
- 「暂未收录」如实写出读不到的部分：S4 平衡调整名单（官方公告是长图；文字版汇总在百度贴吧，需要安全验证，无法读取）、S4 热门阵容（只见于视频和图片；B站接口对程序返回 412 反爬，没有绕过）。
- 换赛季时更新 `season` 和 `items`，并删掉上个赛季的条目。

## 新投稿系统监控

BWIKI 在 2026-07-20～26 重做了投稿：新版要导入官方阵容码（`B~…`），带「适用版本」，页面名为 `阵容:<id>-<名称>`；单只精灵的培养方案存为 `精灵培养方案/…`，先进「待审核」。截至 2026-09-29，真实投稿为 0（只有 1 个测试页）。

刷新脚本每次都会数这两类页面并写入 `meta.json` 的 `source.newSystem`（测试页、没有阵容码的页面不计入）。一旦出现真实投稿，`refresh-meta.yml` 会提一个 issue（只提一次，关闭后也不会重复；提失败不影响刷新）。接入时需要：移植 BWIKI 的 `模块:LineupCode` 解码阵容码，并只收录「适用版本」为当前赛季的投稿。

## 已知局限

- **投稿已停止**：最近一份 PvP 阵容投稿是 2026-06-10，早于 S3（7 月）和 S4（9 月）。页面会显示「最近一份距今 N 天」，并在投稿早于当前赛季开赛时明确写出「不反映当前赛季」。热门配队因此**不含 S4**。
- **技能表是 2026-08-13 的快照**（S3），BWIKI 精灵 596 只，而 data.json 有 622 只；S4 新增内容可能缺失（例如 roco-showdown 更新日志列出的 S4 精灵「果实立方人」，BWIKI 尚无；「云梦豚」「长江豚」则连 data.json 里也没有）。
- 投稿里有 4 只精灵（健猫教练、多灵主、格斗小八、圣代甜甜的口味变体）在 data.json 中找不到或无法唯一对应，9 个技能名不在技能表里，均已在 `meta.json` 的 `source.lineups.unresolvedSpirits / unknownSkills` 中列出，界面上灰显。
- 投稿是玩家自选样本，可能偏向愿意上传的人，且含「自用」「1」之类的随手投稿。

## 技能对位的估算方式

**能量规则**（玩家确认）：每只精灵初始 10 点能量、上限 10、不会自动回复；只有技能自带的回能才能补充。网上没有公开的、可引用的基础数值（BWIKI 只有「初始能量为0」「突破能量上限」这类特性描述），所以这三个数来自玩家确认，改动请同步 `engine.js` 的 `ENERGY_START / ENERGY_CAP`。

`engine.js` 中，比较双方各自**接下来 3 回合内、受能量限制的最大累计输出**：

- 每回合出一招，能量不够就不能出；出招后能量 = min(10, 能量 − 能耗 + 技能自带回能)。
- 对每套社区投稿配招用动态规划排出最优出招，取累计输出最高的一套；带回能的技能（如「徒长」回 10）会在有利时被排进计划。
- 单次伤害 ≈ 威力 × 连击数 × 属性克制 × 攻防种族值比 ÷ 对方生命。
- 没有配招的一方，按「威力 75、能耗 3 的本系技能」估算，两个数是全部攻击技能的中位数。
- 技能自带回能（`meta.json` 的 `refund`）只认固定数值、无条件、回给自己的写法；带「若/每有/应对/击败」条件、回给场下或敌方、数值随场面变化的一律不算，宁可少算。

**窗口长度 3 是估算参数。** 用 12 份热门阵容两两对打（2376 个对位）检验：与旧的不计能耗模型相比，把 ≥6 能耗大招当主力的对位从 15.5% 降到 0.3%；窗口在 2～5 之间变化时，约 6～9% 的判定会变，但几乎都是「均势」边界上的摆动，「占优 ↔ 谨慎」的真正翻转不超过 1%。

**未计入**：本系加成、减耗/追加效果（如「下次技能能耗-6」）、特性、个体值、血脉、变威力技能（如「魔能爆」）。

双属性同时被克制按 3× 而不是 4× 结算：BWIKI 的 `模块:TypeRelation`（2026-06-08）对 ≥4× 封顶为 3，与 2026-04-02 的玩家实测文章一致。

## 定时刷新

`.github/workflows/refresh-meta.yml` 每周一 03:17 UTC 运行（也可在 Actions 页面手动触发）：先跑测试确认基线，抓取，再跑测试验证新数据，仅当 `meta.json` 有变化时提交。保护措施：

- 技能数、PvP 阵容数、作者数比现有文件少 10% 以上，或最近投稿日期倒退，脚本失败并保留旧文件（`--force` 才覆盖）。
- 只有抓取时间不同不算变化，所以 `generatedAt` 表示「内容最近一次变化的抓取时间」，不是最近一次检查的时间。
- GitHub 的计划任务只在**默认分支**上运行；工作流文件合并到默认分支后才会生效。任务失败时 GitHub 会发通知邮件。

## 刷新数据

```sh
npm run meta          # 抓取并覆盖 meta.json，约 30 秒（约 7 次请求）
npm test
```

在需要走代理的环境里加 `NODE_USE_ENV_PROXY=1`。脚本使用带标识的 User-Agent，固定 2.5 秒间隔，遇到 HTTP 567（CDN 限流挑战页）会退避重试；不要缩短间隔或绕过。`--cache DIR` 保存原始响应，`--from-cache DIR` 不联网重新生成。
